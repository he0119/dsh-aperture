# Agent Note: 不写任何配置

Status: implemented

## Problem

写入这块行为（见[写入只碰自己拥有的键](../architecture/2026-09-23-owned-write-plan.md)）的存在理由是让
`llm-pi-ai` 服务本插件发现的路由。它要处理的事情却和「发现」没有关系：别人的配置段、用户的
手写 provider、设置文档的 revision、更高优先级的补丁层、以及历史上用过哪些键。这些都不是本插件
能知道的事——同一份文件里既有用户写的 provider，也有本插件写进去的三条，出了分歧只能靠猜谁对。

真正的代价在于**改的是别人的配置**。用户手写的那一行与插件写的那一行在同一个段里，改一处就可能
把另一处顺手改掉；本插件唯一能做的补救是下一轮刷新再写回去。而升级路径上还有一批遗留键：0.2 及
更早版本写下的 `llm-pi-ai.providers.aperture*` 与现在注册的路由键同名，两边都想服务同一个键。

## Decision

本插件**没有修改配置的能力**：`src/sync.ts`（`planSync` 那套逐键 op）与迁移那一层都不存在，
发现的结果只在这一次运行里注册成路由（见[自带 provider 适配器](../architecture/2026-10-03-own-provider-adapter.md)）。
配置面只剩本插件自己的 `aperture` 段，而那只读、不改——改它的是用户在配置页上按的保存。

路由键的归属因此用一个更小的机制解决：

- 注册前先看 `llm.listProviders()`：想要的路由键已经被别人服务就**不注册**，把那个键与「要手动
  删掉 `llm-pi-ai.providers.<键>`」写进这一轮报告的原因里（配置页把这句话原样显示）。
- 挡住的那一方走开之后本插件要能自己补上，因此它监听 `llm/adapters-updated` 重试；注册成功的一轮
  不再重试（没有自激）。
- 关掉 `sync` 时注册一份空方案，把三条路由撤下来——撤下的是**注册**，不是任何文件里的内容。

## Alternatives considered

**保留写入，只加一层迁移把遗留键删掉。** 那等于让本插件替用户决定「这几个键该删」，而它无法知道
那些键是不是用户自己手写的、是不是还被别的部署在用。报告里点名、让用户自己删，代价只是一次手动
操作，换来的是本插件永远不碰别人的配置。

**保留写入，只是把本插件的键换个前缀避开冲突。** 冲突是症状不是病根：写入本身仍然是「改别人的
配置段」，同一份文件仍然有两个作者。

**只在用户显式要求时才写。** 那要新增一个开关与一整套「写什么、什么时候写」的规矩，而写入换来的
能力（持久化路由）本来就不需要：路由是进程内注册，重启后第一轮发现重新决定，而发现本来就是联网
即得的。

**启动时把遗留键的存在报成一次警告就好，照旧注册。** 同一个路由键有两个服务者时
`registerAdapter` 抛 `DUPLICATE_ADAPTER`，先注册的那一方赢，本插件会整批注册失败——不探测不行。

## Consequences

- 从 0.2 及更早升级上来的部署要**手动删掉** `llm-pi-ai.providers` 下与本插件同名的键，否则那三条
  路由注册不上、配置页会一直显示那一条原因。这条升级说明写在 README 的常见问题里。
- `sync` 这个键名保持不变（`false` = 不注册），但它现在撤下的是注册而不是文件内容；改名的代价是
  老配置里的 `sync: false` 会静默失效。
- 路由是**进程内**的：不落盘、不进备份、跨重启不存在，因此也没有「文件里的路由与运行中的路由不
  一致」这种状态。
- 报告里多了一个可表达的状态：注册失败的原因（`PublishOutcome.reason`）会原样出现在配置页与
  `panel.status()` 的动作结论里。
