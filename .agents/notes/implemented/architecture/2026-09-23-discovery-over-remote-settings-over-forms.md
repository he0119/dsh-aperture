# Agent Note: 发现走 Remote，设置走表单

Status: implemented

## Problem

配置页要读三类东西：发现结果（每轮刷新重写）、逐模型编辑（要在宿主侧读用户层、
按字段合并、把非法值挡在写入之前）、以及两个真正的设置键（`baseUrl`、`sync`）。
三类东西走同一条路会把不同的账混在一起。

## Decision

- **发现结果与逐模型编辑走 Remote**：报告、立刻刷新与逐模型编辑挂在 `aperturePanel`
  命名空间上（`src/remote.ts` 的宿主服务 + `src/panel.ts` 的三个端点）。
- **地址与同步开关不走 Remote**：它们就是设置文档里的两个键，因此按设置命名空间自己
  取——`ctx.configForms.get('aperture')`，服务按命名空间缓存控制器，拿到的与插件页
  自己那份是同一个。它给出的快照就是官方设置表单要的那个作用域（`status` / `value`
  / `base` / `user` / `revision` / `writable`），于是草稿、脏标记、`revision` 围栏
  写入、冲突拒绝、只读与「命名空间没在服务」的说明全交给设置接缝
  （`SettingsFormModel`），本插件不复制一套。`configForms` 缺席时表单接到一个
  `unavailable` 替身上，报告照旧显示。
- **报告是数据，不是句子**：`src/report.ts` 只组装结构（哪个模型属于哪条路由、每条
  事实来自哪里、用户写了哪些覆盖），措辞与排版都在 Web Client 端按语言组织。
- **写完等一轮刷新落地才回答**：两条写路径在写入之后都
  `await runtime.refresh('配置变更')`。

## Alternatives considered

**把发现结果塞进设置文档。** 那会让「用户写了什么」与「插件发现了什么」混成同一份
账，而后者每轮刷新都会被重写。

**让界面直接改设置文档。** 逐模型编辑得先读用户层、按字段合并、把非法值挡在写入
之前——这些判断属于插件而不是界面。

**报告在 Host 端拼成句子。** 配置页是双语的，把中文句子拼在 Host 端等于让英文界面
显示中文。

**写完就回答，靠界面自己再读一次。** 报告里的路由与模型事实来自最近一次刷新，不等
它，界面重读到的还是旧配置算出来的那一份，也就是「保存了却没变」。这里不必担心多跑
一轮：设置变更本身就会唤起同一轮刷新。

## Consequences

- 报告里的「已覆盖」与别名来自实时配置，路由与容量来自最近一次刷新——两处的时间点
  不同，界面必须能说出这一点。
- `refresh` 的承诺是「返回的那一轮读的是**此刻**的配置」：正在跑的那一轮读的就是
  此刻这份配置时调用方并进它，读的是更早的配置时才排到它后面（排队者共享排上的那
  一轮）。配置的身份可以直接比：设置服务每次提交都换一份深冻结的解析结果。
- 动作端点仍是「Host 端说一句话」的形态（`PanelAction.summary`），因此英文界面里
  那一行也是中文（见[已知边界](../../../../docs/internals.md)）。
