# Agent Note: 刷新必须从 HMR 事务之外起跑

Status: implemented

## Problem

设置写入整次都在事务里：`config-editor.edit()` 把 `run()` 包在
`hmr.runExclusive()` 里，而 `loader/volatile-update` 正是在那个事务里**同步**发出来
的。事务的 AsyncLocalStorage 印记会跟着从事件处理器里起的 promise 链一路走，事件那
一轮早跑完了也不掉。于是直接在事件里刷新，那一轮对本配置段的写入就会被判成事务嵌套
而拒绝（`HMR transactions cannot be nested`）。

表现上最容易被误判：发现本身看起来是成功的（模型列表、路由、耗时都在），只有宿主日志里那句
「注册发现的路由失败」说的是实话，配置页上显示成「没注册（…）」。最典型的一步是**填地址那次
保存**：地址空着时插件是休眠的（启动那一轮不发请求），第一次真正要做事（那时是写
`llm-pi-ai` 的配置段）的时刻恰好就是这次配置写入打开的事务里。

本插件现在不写配置，因此这条规矩眼下不是被某一次「写入被拒」逼出来的；它挡的是同一类形状：
印记会沿着我们从事件里起的 promise 链一路传下去，而那一轮刷新会经 `llm.registerAdapter` 发出
`llm/adapters-updated`——宿主的每个监听者都在同一条链上，任何一环做 HMR 工作就会撞上嵌套拒绝，
失败只留在宿主日志里。

## Decision

每一轮刷新都交给 `src/relay.ts` 那条通道起跑：它在**模块作用域**被拉起（模块求值
不在任何事务里），事务里只负责把它叫醒；作业的续体注册在通道自己的上下文里，于是
整轮都在事务之外，而写入照旧排在 HMR 队列后面（换的是上下文，不是串行）。

通道按**模块**持有而不是按插件实例：源码热重载会让插件在事务里重建，实例里拉起的
通道会跟着带上印记，而本模块通常留在模块缓存里。定时器、事件、插件加载三条来路都
经它——它们是同一个问题的三种现场。

## Alternatives considered

**在事件处理器里直接刷新。** 就是上面那个现象：这一轮写入被事务嵌套拒绝，而发现
看起来是成功的。

**把通道按插件实例持有。** 源码热重载会让插件在事务里重建，实例里拉起的通道跟着
带上印记，等于把问题原样搬回来。

**不做自动刷新，等用户手动点「立刻刷新」。** 配置页拿到回答就会重读报告，而报告来自
最近一次刷新；不自动刷新等于让用户在两处之间自己找因果关系。

## Consequences

- 事务里只负责叫醒，不做任何事；判断「这一轮在不在事务里」的地方只剩通道一处。
- 端到端那份把一个替身 `hmr` 挂进 profile（只留 `runExclusive()` 的两条语义），于是「刷新有没有
  带上面包屑」这件事在真实形状里被测到，而不是靠推断（见[三份测试各证什么]
  (../testing/2026-09-24-three-test-layers.md)）。
